# フルリモートFDEジョブエイド（閉域ローカルLLM導入編）

## 日本流FDEの骨格との対応

IoT検定制度委員会の「FDE検定」構想（2026年）は、FDEを
**「AI前提で業務を再設計し、現場に定着させ、KPI改善などの成果を継続的に創出できる人材」**
と定義し、知識・応用力（レベル1）→実装力（レベル2）→成果実績・再現性（レベル3）の
3段で評価するとしている（出典: [iotcert.org/fdekentei](https://www.iotcert.org/fdekentei/)）。

そこから抜き出せる共通の骨格は「業務理解・課題特定 → 設計 → 実装 → 定着（教育・指導）→ 成果（KPI）」の
5段である。本リポジトリはこれに**6段目として「再現性」**を加える。検定制度が最上位（レベル3）で
ようやく評価する再現性を、全工程の出口条件——誰がやっても同じ結果になる状態で渡すこと——として
最後に置くのが、この道具箱の立場である。

| 骨格 | 本リポジトリでの対応 |
|---|---|
| 1. 業務理解・課題特定 | ジョブエイド フェーズ0-1（契約条項・データ区分・環境同等性のヒアリング） |
| 2. 設計 | 配置判定（cloud-or-local.html）、方式の実測選定（rag.py のk掃引）、モデル受け入れ検査（model-check/） |
| 3. 実装 | 7.6GBで動く構成（genai/）、相手が実行する前提の手順書（フェーズ3） |
| 4. 定着（教育・指導） | ブラウザUI（非技術職員向け）、運用引き渡し（フェーズ5） |
| 5. 成果（KPI） | 原典照合による検収（check.py）、非送信証跡（evidence.py）、実測値の記録 |
| **6. ＋再現性** | 全コード・手順・実測値の公開、SHA-256による文書・モデルの同一性確認、ハッシュチェーンの第三者再検証（誰でも verify を再実行できる） |

3段の評価階段に対しては、学習の証跡（learning-log/）が知識・応用力の記録、
本リポジトリの公開コードと実測値が実装力の実物、KPI付きの実績報告が成果実績の記録、
という形でそれぞれ対応する。

---

FDE（Forward Deployed Engineer）は、顧客側に入り込み、要件のヒアリングから
導入・定着までを一貫して担うエンジニア職。米Palantir発祥で、2025年以降は
日本のAI企業・SaaS各社の採用職種にも広がっている。

FDEの定義は「現場に入る」ことだが、閉域環境の案件では、外部の受託者は
そもそも現場のネットワークに入れないことが多い。本ジョブエイドは、
**現場に入れない前提で閉域ローカルLLM導入を成立させる**ための確認手順を、
本リポジトリの実測記録（機材構成の同等性検証・出力の照合・非送信証跡）に
基づいて6フェーズにまとめたものである。

## 使い方

[jobaid.html](jobaid.html) をブラウザで開くだけ。

- 単一HTMLファイル。外部リソースの読み込み・外部送信なし。オフラインで動く
- チェック状態とメモはそのブラウザのlocalStorageにのみ保存される
- 「印刷」ボタンでPDF化し、案件記録として残せる

## 生成AI配置判定エイド（cloud-or-local.html）

[cloud-or-local.html](cloud-or-local.html) は、扱うデータの中身・契約条件・実行環境の
3問に答えると、「約款型クラウドAI／専用環境（ガバメントクラウド・オンプレ）／
ローカルLLM」のどれが妥当かと、その根拠を返す単一HTMLツール。

デジタル庁 DS-920「生成AIの調達・利活用に係るガイドライン」（2025年5月）の
公開基準に基づく。ガバメントクラウドの対象CSP（AWS・Microsoft Azure・
Google Cloud・Oracle Cloud・さくらのクラウド）を前提に、クラウドを排除せず
「クラウドで良い場合」と「ローカルしかない場合」を分けて示す。
機密性区分の番号は団体により付け方が逆転しうるため、名称でなく中身で
選ばせる設計にしている。

## ジョブエイドのフェーズ構成

0. 案件開始前 — 契約・条項（生成AI利用可否条項、データ区分の確定）
1. リモートヒアリング — 環境の同等性（メモリ割当、モデルサイズ、閉域条件）
2. 手元での同等環境検証（文書の同一性確認、方式の実測選定）
3. 導入 — 相手が実行する前提の手順書
4. 検収 — 出力の照合と非送信の証明
5. 引き渡し・運用
