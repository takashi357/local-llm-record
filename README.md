# 閉域環境でのローカルLLM：出力検収の記録と関連ツール

## 概要（30秒で読めます）

- **問い**：インターネットに接続しない（閉域の）PCでローカルLLMに規程文書を読ませたとき、守るべき事項を漏れなく抜き出せるか。抜き出せたかを、どう確かめるか。
- **方法**：自治体が公開している生成AI利用ガイドラインを題材に、通信を遮断したWindowsノート1台で、全文を渡す方式とRAG（関連部分だけを検索して渡す方式）を比較しました。出力は原典の遵守事項6項目と1行ずつ照合しています。
- **結果**：全文を渡すと6項目すべてが出力されました（欠落0件）。RAGでは、23チャンク中12チャンクを渡しても4項目にとどまり、遵守事項の本体が書かれた章が一度も検索で選ばれていませんでした。
- **私の役割**：検証の設計、判定基準の作成、実機での実行、出力と原典の照合です。スクリプトの作成にはAIコーディング支援を使いました。照合スクリプトの初版には誤判定があり、私が出力と原典を突き合わせて発見し、修正しています。

本リポジトリには、この測定記録に加えて、閉域でローカルLLMを導入・運用するための関連ツール（[下記](#関連ツール)）も収録しています。

## 測定内容

通信を遮断したノートPC1台で、自治体が公開しているガイドラインから利用者が守るべき事項を抽出させ、その出力を原典の項目と照合します。

### ファイル構成

- `run.py` … 文書の全文と設問をローカルのモデルに渡し、遵守事項の表を作成させる
- `check.py` … 出力された表の各行を原典の項目と突き合わせ、該当した行・該当しなかった行・欠落した項目・重複を出力する
- `rag.py` … 全文の代わりに、設問に近いチャンクだけを抜き出して渡す
- `out.txt`、`out_k*.txt` … 実行時のモデル出力（全文を渡した場合と、k件を渡した場合）
- `measurements/` … 実測の詳細と出力全文

### 背景

同じ端末・同じモデル・同じ文書でも、アプリの画面から実行すると文書の一部しか渡されず、重要な項目が欠落することがありました。全文を自分で渡す形（run.py）にすると、欠落はなくなりました。

また、照合する側にも誤りがありました。初版は表記の揺れを吸収できず、出力に含まれている項目を「現れなかった」と誤って報告しました。出力を検査する仕組みそのものも、検査が必要です。

### 抜き出して渡す場合（rag.py）

同じ端末・同じ文書・同じ設問で、全文の代わりに関連しそうな箇所だけを渡した記録です。

文書を800字ごと（150字重複）に区切ると23チャンクになります。設問との類似度が高い順に上位k件を選び、それだけを渡して同じ表を作成させました。埋め込みモデルには nomic-embed-text-v1.5 を使用しています。追加ライブラリは使っていません。

### 対象文書

福岡県「生成AI庁内利活用ガイドライン（第2.2版）」（令和8年4月1日）

原典: https://www.pref.fukuoka.lg.jp/uploaded/attachment/282910.pdf

本文（gl.txt）は転載を避けるため同梱していません。再現する場合は、上記PDFからテキストを抽出し、`gl.txt` として同じフォルダに置いてください。同一性の確認用に、使用したファイルの値を記載します。

- サイズ: 34,047バイト（UTF-8）
- SHA-256: 65de069774b147fd1dbb028c4cea8c334ed92f882a1041ad1d46202c35ce94b5
- チャンク数（800字・150字重複）: 23

抽出方法の違いで改行や空白が変わると、これらの値は一致せず、区切り位置もずれるため結果が変わる可能性があります。

## 動作環境

- Windows 11 / Python 3.13（標準ライブラリのみ）
- LM Studio 0.4.20 のローカルサーバー（http://127.0.0.1:1234）
- モデル: openai/gpt-oss-20b（GGUF・MXFP4・12.11GB）
- コンテキスト長 32768 / temperature 0
- メモリ16GBの端末でWSL上のLinuxを使う場合、既定のメモリ割り当ては7.6GBのため、12.11GBの本モデルは読み込めません。詳細は `measurements/` を参照してください。

## 実行手順

### 全文を渡す場合

1. LM Studioでモデルを読み込み、Developer → Start Server
2. 対象文書のテキストを `gl.txt` として同じフォルダに置く
3. `python run.py` → 出力が `out.txt` に保存される
4. `python check.py` → 照合結果が表示される

### 抜き出して渡す場合

```
python rag.py 3
```

引数はkです。出力は `out_k3.txt` に保存されます。すべての実行は機内モードで行いました。

## 結果

### 全文を渡した場合

- 入力 8,343トークン / 出力 874トークン / 所要 81.54秒
- 出力10行に、原典の遵守事項6項目がすべて含まれていた（欠落0件）

### 抜き出して渡した場合

| k | 入力トークン | 所要秒 | 出力行数 | 遵守6項目 | 選ばれたチャンク |
|---|---|---|---|---|---|
| 3 | 1,909 | 46.55 | 5 | 1 | 12,16,19 |
| 5 | 3,087 | 50.10 | 4 | 0 | 11,12,16,17,19 |
| 8 | 4,793 | 70.49 | 7 | 2 | 9〜12,16,17,19,20 |
| 12 | 7,019 | 66.86 | 7 | 4 | 7〜12,15〜20 |
| 23 | 10,256 | 91.20 | 10 | 6 | 全件 |

遵守6項目：QT-GenAIに限定／使用対象者の限定／テキスト以外の制限／機密性1（個人情報）の禁止／約款型サービスの事前協議／生成内容の信頼性確認

（「QT-GenAI」は、対象ガイドラインが利用を認めている生成AIサービスの名称です。）

6項目の判定は、出力の各行が原典の規定と同じ義務を述べているかを1行ずつ照合して行いました。単語の一致による自動判定は、無関係な行を拾ったり言い換えた行を落としたりする誤りが出たため、採用していません。

## 考察

**全件を渡す場合を除き、6項目が揃うことはありませんでした。** 半分の12チャンクを渡しても4項目にとどまり、全23チャンクを渡してようやく6項目が揃いました。

**件数を増やせば単調に改善するわけでもありません。** k=3では5行・1項目、k=5では4行・0項目と、渡す量を増やしたのに行数も項目数も減りました。出力の内容も入れ替わり、k=3とk=5で共通する行は1つだけでした。

**削減効果も限定的です。** k=12の入力は7,019トークンで、全件（10,256トークン）の約7割にあたります。入力を減らすために抜き出しているにもかかわらず、7割を渡しても2項目が欠落しました。

**最大の要因は、どのチャンクが選ばれたかです。** 義務の本体が書かれた章（2.1）はチャンク13〜15にありますが、このうち13と14は、k=3・5・8・12のいずれでも一度も選ばれませんでした。守るべき事項を問う設問なのに、その章を参照しないまま表が作成されていたことになります。k=8以降に現れた「QT-GenAIに限定」や「事前協議」は、第4章（対象外サービスの章）にある同じ内容の記述から拾われたものです。

出典として示される章が揺れた原因もここにあります。同じ規定が2.1と第4章の2か所に書かれているため、どちらのチャンクが渡されたかによって、同じ義務に別の章が出典として付きました。

## 前提と限界

- 結果は、この文書・この区切り方・この埋め込みモデルの組み合わせでのものです。
- k=23は全チャンクを渡しており、実質的には全文を渡した場合と同じ状態です。「23件なら足りる」という意味ではありません。
- k=23の入力（10,256トークン）が全文（8,343トークン）より多いのは、チャンクの重複部分（150字×22か所）が重ねて渡されるためです。

## 関連ツール

上記の測定記録を土台に、閉域でローカルLLMを導入・運用するためのツールを作成しました。

- [model-check/](model-check/) — **モデルの受け入れ検査**。公開リポジトリから取得したモデルファイルを、実行せずに検査します（pickle形式の拒否、GGUF／safetensorsのヘッダ解析、SHA-256照合、メモリに載るかの判定）。
- [genai/](genai/) — **少ないメモリで動く閉域RAG**。上記「動作環境」の制約（WSLの割り当て7.6GBでは12.11GBのモデルが載らない）への対応として、gemma3:4b＋bge-m3（2つ合わせて約4.5GB）に収めた構成です。実行ごとに外部への通信がないことを確認し、入出力のハッシュを連鎖させて記録します。ブラウザUI付きで、Python標準ライブラリと素のHTML/CSS/JSのみで実装しています。
- [fde/](fde/) — **導入支援のチェックリスト**。現場に入ってAI導入を進める役割（FDE：Forward Deployed Engineer）を想定した、リモートでの作業チェックリスト（6フェーズ24項目）と、デジタル庁の基準（DS-920）に沿って生成AIの利用形態（約款型サービス／専用環境／ローカル）を判定する補助ツールです。
