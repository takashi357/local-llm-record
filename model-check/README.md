# モデル受け入れ検査 — 閉域環境に持ち込む前の確認

公開リポジトリ（Hugging Face など）から取得したモデルファイルを**実行せずに**検査するツールと、配布ページで人が確認すべきチェックリストです。閉域環境（インターネットに接続しない環境）にモデルを持ち込む前の、受け入れ検査にあたります。

## なぜ必要か（2026年時点の状況）

- モデルの保存形式として主流だった pickle 系（.pt / .bin など）は、**読み込んだ時点で任意のコードが実行される可能性があります**。Hugging Face 上の悪意あるモデルによる攻撃は、2024年以降繰り返し確認されています
- 検出ツール（PickleScan）自体にも、検査をすり抜けられる脆弱性（CVSS 9.3、3件）が見つかっています。**「スキャン済み」であることは安全の保証になりません**
- 2026年には、モデルの config.json に細工をすることで、`trust_remote_code=False` の設定でもコードを実行させられる脆弱性（transformers ライブラリ）も公表されました
- これに対して GGUF / safetensors は、**コードを含まないデータ形式**です。Ollama / LM Studio 経由のローカルLLM運用ではこれらの形式しか使わないため、pickle 系のリスクを最初から持ち込まずに済みます

## 使い方

```bash
# 基本検査（形式・メタデータ・メモリ適合）
python3 modelcheck.py model.gguf

# 配布元の公表ハッシュと照合
python3 modelcheck.py model.gguf --expect-sha256 <64桁>

# 取得記録（いつ・どこから・何を）をハッシュチェーンで残す
python3 modelcheck.py model.gguf --record "https://huggingface.co/..."
```

検査内容は次のとおりです。

- pickle 系のファイルは開かずに不合格とする
- GGUF はマジックナンバーとメタデータ（アーキテクチャ・ライセンス・量子化・出所）を解析する
- safetensors はヘッダを検証する
- SHA-256 を計算し、公表値と照合する
- 実行環境のメモリに載るかを判定する（1.2倍の余裕を見込む）

## 配布ページで人が確認すること（チェックリストA）

- **A-1 出所**: 発行元の organization（組織アカウント）は本物か。モデル名が本物に似せた偽名（タイポスクワット。例: `meta-11ama`）になっていないか。ダウンロード数や更新履歴に不自然な点はないか
- **A-2 形式**: GGUF か safetensors のみを受け入れる。.pt / .bin しかないモデルは選び直す
- **A-3 ライセンス**: 商用利用・再配布の条件を確認する（Apache／MIT／Gemma／Llama などで、それぞれ異なる）。委託成果物に組み込めるかは、契約内容と突き合わせる
- **A-4 実行側の設定**: `trust_remote_code=True` は使わない。transformers を使う場合は最新版を保つ（config.json 経由の任意コード実行が修正された版か確認する）。Ollama / LM Studio 経由であれば、この経路はもともと存在しない
- **A-5 記録**: 取得URL・SHA-256・日時を `--record` で残す。閉域環境へ搬入した後に、「検査済みのファイルと同じものか」をハッシュで照合できるようにする

## 本リポジトリでの位置づけ（導入から定着まで）

1. **入口** — このツールによる受け入れ検査（このフォルダ）
2. **配置判定** — クラウドかローカルか（fde/cloud-or-local.html）
3. **構築** — WSLのメモリ割り当て7.6GBで動く構成（genai/）
4. **検収** — 出力の照合と非送信の証跡（check.py・genai/evidence.py）
5. **定着** — フルリモートFDEジョブエイド（fde/jobaid.html）の手順書・引き渡しフェーズ
