# 一般的な業務用ノートPCで、どのモデルが実用になるか

手元のノートPC（メモリ16GB、WSL＋Ollama）で、ローカルLLMのモデルを比較した記録です。

本リポジトリの測定用スクリプト（run.py・rag.py）は、gpt-oss-20b（12.11GB）を前提としています。では、業務で一般的に使われるノートPCでも動かせるのでしょうか。その前提条件を確かめるため、端末の制約と、その制約の中で動くモデルの実力を測りました。

## 結論

1. メモリ16GBの端末でWSL（Windows上でLinuxを動かす仕組み）を使うと、Linux側へのメモリ割り当ては既定で7.6GBです。12.11GBのモデルは、この既定値のままでは読み込めません。
2. 7.6GBの枠内でも、モデルを選べば実用的な速度と自然な日本語を両立できます。ただし、容量の大きさと速度・品質は比例しません。3.3GBのモデルが5.2GBのモデルより約2倍速く、日本語も自然でした。
3. 日本語が自然なモデルほど、誤りに気づきにくくなります。この測定では、最も日本語が自然だったモデルが、根拠のない金額を出力しました。

## 測定環境

| 項目 | 値 |
|---|---|
| OS | Windows 11 |
| Linux 実行環境 | WSL 2.7.12 + Ubuntu 26.04 LTS |
| メモリ | 16.0GB LPDDR4-4267（うち WSL 割当 7.6GB、swap 2.0GB） |
| GPU | Intel Iris Xe（内蔵。専用 VRAM なし） |
| 推論エンジン | Ollama |
| 測定日 | 2026-08-23 |

専用のグラフィックボードは搭載していないため、推論は主にCPUで行われます。

## 設問

```
納付書を紛失したという問い合わせに対する窓口回答を、敬語で3文以内で書いてください。
```

同じ設問を各モデルに3回ずつ入力しました。パラメータは既定値のまま変更していません。

qwen3は回答の前に推論過程を英語で出力する仕様のため、出力トークン数が増え、総所要時間が長くなります。

各モデルとも、1回目だけはモデルの読み込み時間が加わります（qwen3で9.42秒、gemma3で5.59秒）。連続して実行した2回目以降は、読み込み時間はミリ秒単位に収まります。速度を比べる際は、1回目を除外するのが妥当です。

## 所見

### 生成速度は安定しているが、総所要時間はばらつく

生成速度は、同じモデルであればほぼ一定です。gemma3は12.31 / 12.30 / 12.33 tok/sと、3回でほぼ完全に一致しました。一方、総所要時間は3.8〜10.8秒とばらつきました。原因は処理速度ではなく、出力の長さです。

そのため、所要時間にしきい値を設けて運用すると、出力の長さによる変動をそのまま受けることになります。

### 「3文以内」の指示は、どのモデルも守り切れなかった

| モデル | 3文以内の遵守 |
|---|---|
| llama3.2:3b | 3回中2回 |
| gemma3:4b | 3回中0回（全回4文） |
| qwen3:8b | 3回中1回 |

日本語として最も自然だったgemma3が、文数の制約を最も守っていませんでした。文章の自然さと、指示に従う力は別の性質だといえます。

### 日本語の破綻（llama3.2:3b）

- 「ごみ箱などに捨てられている可能性がありますようになります。ごみ箱の確認をしてみてください。」
- 「ご紛失になったためご迷惑をおかけしたことを sincerest apologies で表します。」（英語混入）
- 「弊社」「直営店」など、行政窓口ではなく企業の応対で使う語彙

この水準の出力であれば、読めば誤りだと分かります。

### 根拠のない情報と、誤った案内（gemma3:4b、qwen3:8b）

gemma3の1回目の出力に、次の一文が含まれていました。

> 再発行の手続きにつきましては、手数料300円をご負担いただきます。

設問には金額の情報は含まれておらず、300円という数値には根拠がありません。

敬語は正しく、文の流れも自然で、窓口回答として成り立っているように見えます。破綻した日本語なら誰でも気づいて捨てられますが、この種の誤りは原典と照合しなければ見つけられません。

また、qwen3の3回目には「お支払いの銀行または関係部署までお問い合わせください」という、案内先の誤りも出ています。納付書の再発行は発行元の窓口が扱う事務であり、銀行の所管ではありません。

金額・期限・所管部署を含む出力は、原典と照合する工程を通さない限り、そのままでは使えません。本リポジトリの照合ツール（check.py）は、この性質に対応するために作成したものです。

## 前提と限界

- 設問は1種類のみです。文書の要約や抽出など、他の作業では傾向が異なる可能性があります
- 各モデル3回ずつの測定で、統計的な有意性を主張できる回数ではありません
- 端末は1台のみです。CPUの世代やメモリ帯域が異なれば、速度は変わります
- 量子化形式はOllamaの既定値に依存しており、モデル間で条件が完全には揃っていません
- 出力の良し悪しは私が判断しました。第三者による評価は行っていません
